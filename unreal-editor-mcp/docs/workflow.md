# Feature workflow

Use this workflow for every feature, fix, or refactor.

1. Start at [`index.md`](index.md). Read the owning architecture page and affected type indexes, then inspect the relevant source, tests, metadata, examples, history, roadmap, and user documentation. Expand the working set only when evidence reveals another dependency.
2. Use [`../ROADMAP.md`](../ROADMAP.md) and the relevant feature document under [`features/`](features/index.md) only for intended scope. Assign new responsibility to one component; trace Python/C++ data, commands, errors, limits, versions, operations, Blueprint state, and Game-thread dispatch. Validate bounded schemas on both sides.
3. Make the smallest coherent change. Add proportional normal, invalid, limit, security, and platform coverage; run focused tests, then the full suite after behavior changes. Run Unreal Automation and headless/command-line checks for editor changes and cross-process tests for bridge changes.
4. Update changed architecture/type references and their immediate indexes. Update `README.md` for user-visible changes and `HISTORY.md` or `ROADMAP.md` for release/scope changes. From the repository root, run `python internal/tools/lint_docs.py` after Markdown changes.
5. For a release, synchronize Python and `.uplugin` metadata, runtime capabilities, tests, examples, and history.

## Implementation rules

- Use ignored `ue-test/ue57/` only as the disposable Unreal Engine 5.7 build and integration-test project; never treat its generated state as a committed contract.
- Build changes from small typed mutations. Prevalidate targets, types, limits, and stale state; use editor transactions where supported; expose bounded compile, save, and read-back results; preserve unrelated Blueprint content.
- Keep the C++ bridge localhost-only and authenticate every request with a durable, high-entropy per-project token. Fail closed on credential errors and never expose the token through discovery or heartbeat data.
- Isolate and test platform-specific discovery, paths, plugin loading, and process behavior. Validate editor changes with Unreal Automation, headless/command-line, and cross-process tests as applicable.
- Treat Windows support as mandatory for the base plugin, companion plugins, and every feature. Do not complete or release a feature until its applicable Windows build, packaging, native Automation, headless/command-line, and cross-process checks pass.
- Treat macOS support and native verification as preferred follow-up work, not a completion or release gate. A feature may release before macOS verification or known macOS bug checks finish; record the outstanding feature under the `ROADMAP.md` macOS native platform test backlog and remove it after verification passes.
- Treat Linux as outside the current support and verification scope. Linux builds, packaging, native tests, compatibility-branch tests, and source-portability evidence are not required, do not block a release, and must not be claimed as supported without a later explicit policy change.
- Keep the `ROADMAP.md` native platform test backlog current whenever a feature is completed or native test evidence changes. Unresolved mandatory Windows verification keeps a feature unfinished rather than creating a completed-feature backlog entry. Under macOS, list each completed feature that still lacks its applicable preferred verification, remove it after verification passes, and write `None` when no follow-up remains. Do not maintain a Linux backlog while Linux is out of scope.
- For destructive asset mutation, a truncated bounded live-memory diagnostic is not by itself a reference-safety failure when every registry reference category is complete and current, the diagnostic is supported and not stale, it reports no references, and Unreal's full deletion-specific memory and Undo reference check also succeeds. Reject unsupported or stale live diagnostics, truncated registry scans, any observed reference, or an incomplete full Unreal check.

## Companion plugin API and version workflow

- The base plugin and every companion plugin declare one explicit positive integer `companion_api_version`; the initial value is `1`. This is the global native host-to-companion API version, not a plugin semantic version, MCP protocol version, Python/native protocol version, extension-schema revision, or Unreal Engine version.
- Store `companion_api_version` in required base and companion `.uplugin` metadata and in compiled constants. Discovery checks descriptor values before registration; registration checks compiled base and companion constants and verifies each against its descriptor. A missing value, any disagreement, or a stale binary fails closed and exposes none of that companion's functionality.
- Require exact equality between the base and every loaded companion. Increment `companion_api_version` for every change to how the base and companions communicate, including additive API changes. Do not publish compatibility ranges, default a missing value, or leave an old companion registered.
- Before changing the companion API or incrementing `companion_api_version`, stop and give the user an impact report that names every companion and test fixture, required API migration, semantic-version bump, packaging effect, and validation obligation. Ask for explicit permission to continue even when the initiating request already asks for a companion API change. Do not edit the API, version, or dependents until that permission is received.
- After approval, update every companion and companion test fixture in the same task. A companion unrelated to the behavior change still receives the API update, rebuild and regression coverage, and a patch-version bump. Do not defer an old-API companion or complete with a mixed API-version set.
- Version the base and each companion independently with the same semantic-version policy: major only when explicitly requested by the user; minor for every new feature or improvement; patch for every bugfix or compatibility-only companion API update. When categories overlap, apply the highest bump. An API-changing feature therefore gives the substantively changed plugin a minor bump and API-only companion updates a patch bump.
- Synchronize every version source owned by each plugin, but never require a companion's `Version` or `VersionName` to equal the base plugin's semantic version. Release-contract tests cover each plugin's internal semantic-version consistency, descriptor and compiled `companion_api_version` consistency, equality of the global API version across the complete companion set, extension-schema compatibility, and the independently required Python/base-plugin version contract.
